# Dashboard: Link Analytics, Workspace Overview and Account Settings — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The screens that make the numbers useful: a link's own analytics with a date range, a bot toggle, a chart, breakdown panels, an hour-by-weekday heatmap and a live recent-clicks stream; a workspace overview with a leaderboard; a CSV export; and the account settings page the product has been missing.

**Architecture:** Views are thin readers over `apps.analytics.queries`, which is the only data source — no new queries, no model access from templates. One page shell loads, and every control (range, granularity, bot toggle) swaps a single `#analytics-body` fragment with `hx-push-url`, so a reload reproduces the view. Charts are vendored Chart.js reading their data from a `<script type="application/json">` next to each canvas, re-initialised on `htmx:afterSwap`. The heatmap is a CSS grid, not a chart. Styling uses the tokens and component patterns already in the repository; no new design system.

**Tech Stack:** Django 6.1 templates, HTMX, vendored Chart.js 4, the existing Tailwind token set.

**Spec:** `docs/superpowers/specs/2026-09-17-short-design.md` section 7. Design reference: `docs/design/README.md` and `docs/design/screens/{analytics,overview,account}.html` — follow their structure and copy, built with the components already in `templates/`.

## Global Constraints

- English everywhere; commits `GH-<issue>-<type>: description` on branch `GH-<issue>`; no AI attribution.
- Views read only through `apps.analytics.queries`; they never build a queryset over `ClickEvent` or the rollups themselves.
- Every analytics route carries `@require_role()` and is scoped by `request.workspace`.
- One fragment id, `#analytics-body`, is what the controls swap, with `hx-push-url="true"` so the URL always describes the view.
- Chart data reaches JavaScript through `json_script`, never interpolated. The one chart module is registered once and re-runs on `htmx:afterSwap`. Inline scripts carry `nonce="{{ csp_nonce }}"`.
- Colours, spacing, radii and type come from the existing tokens in `assets/css/app.css`. The accent is the only saturated colour; the heatmap uses accent at varying alpha.
- Every screen works at 390 pixels wide: panels stack, the table becomes cards, the heatmap scrolls horizontally rather than shrinking below legibility.
- Empty states are real screens, not blank panels, and say what to do next.
- Tests: `uv run pytest` 0 warnings; ruff, pre-commit and `makemigrations --check` clean.

### Task 1: Filters, the link analytics shell and its body

**Files:** create `apps/analytics/forms.py`, `apps/analytics/views.py`, `apps/analytics/urls.py`, `templates/analytics/link.html`, `templates/analytics/partials/{body,kpis,filters,empty}.html`, `tests/analytics/test_views_link.py`; modify `config/urls.py`, `templates/dashboard/base.html`, `templates/links/partials/row.html` (an Analytics action per row).

**Interfaces:** route `analytics:link` at `/w/<slug>/links/<code>/analytics/`; `AnalyticsFilterForm` cleaning `range` (7d, 30d, 90d, custom), `start`, `end`, `granularity` (day), `include_bots`; a `filters` context object carrying the resolved start and end dates and the query string that reproduces them.

- [ ] **Step 1: Write the failing tests**

`tests/analytics/test_views_link.py` covers: the page renders for a member and 404s for an outsider and for a code in another workspace; the default range is the last 7 days and the KPI values match `queries.summary` for that window; `?range=30d` changes both the numbers and the pushed URL; a custom range with explicit dates is honoured and an invalid one falls back to the default with a visible message rather than an error; `?include_bots=1` raises the totals and the toggle reflects the state; an HTMX request returns only the body fragment while a normal request returns the whole page; a link with no clicks renders the empty state with a copy button and no chart; the recent-clicks list is present and polls; and the page never renders an address or a user agent.

- [ ] **Step 2: Run to verify they fail, then implement**

`AnalyticsFilterForm` resolves a range into two dates in the workspace's timezone, clamps a custom range to the retention window, and exposes `as_query()` for building HTMX URLs. The view calls `queries.summary`, `queries.time_series`, `queries.breakdown` for each dimension it shows, `queries.hour_weekday_matrix` and `queries.recent_clicks`, then renders `link.html` or, for an HTMX request, `partials/body.html`.

`link.html` extends `templates/dashboard/base.html`: a header with the short code in mono, the destination, copy and QR buttons (QR stays disabled with a title until its own issue), an Edit link, then `{% include "analytics/partials/filters.html" %}` and `<div id="analytics-body">{% include "analytics/partials/body.html" %}</div>`.

`filters.html` renders the range chips, the granularity select, the bot toggle and the export link, each with `hx-get` targeting `#analytics-body`, `hx-push-url="true"` and `hx-include="closest form"`.

`kpis.html` renders four tiles — total clicks, unique clicks, top country, top referrer — each with its delta, using the existing card and muted-label patterns. A `None` delta renders as a dash, not "+100%".

`empty.html` is the zero-click state: the chevron mark, "No clicks yet", "Share the link and data lands here within seconds", and a copy button.

### Task 2: Charts, panels and the heatmap

**Files:** create `static/js/charts.js`, `templates/analytics/partials/{chart,panels,panel,heatmap,recent}.html`; modify `templates/base.html` (load the chart module), `tests/analytics/test_views_link.py`.

**Interfaces:** `charts.js` finds every `[data-chart]` canvas, reads the JSON from the `<script type="application/json">` whose id the canvas names, draws it, and redraws after an HTMX swap; it reads its colours from the CSS custom properties so both themes work.

- [ ] **Step 1: Write the failing tests**

Extend the link tests: the chart's JSON payload contains one point per day in the range including zero-filled gaps, and both series; each breakdown panel renders its rows with a share bar and a "more" count when there are more values than shown; the heatmap renders 7 rows of 24 cells with an accessible label per cell; the recent list renders the anonymised columns and carries the poll attributes. Add a small JavaScript-free assertion that the page contains no inline event handlers.

- [ ] **Step 2: Implement**

`chart.html` renders the canvas and its JSON payload. `panels.html` loops the dimensions the design lists — referrers, countries, cities, devices and operating systems, browsers, UTM source and medium, and for a device-routed link the destination split — including `panel.html` for each. `panel.html` renders a title, a row per value with a bar whose width is the share, the value, the count and the share, plus a muted "+N more". `heatmap.html` is a CSS grid of 7×24 cells whose background is the accent at an alpha derived from the value, with hour labels every three columns and a low-to-high legend; each cell carries a title attribute naming the weekday, hour and count. `recent.html` renders time, device and browser, referrer host, country and city, with `hx-get` on a 20-second trigger swapping only itself.

`charts.js` is vendored-Chart.js wiring only: no data, no styling literals beyond reading CSS variables. Register it in `base.html` with the nonce, after Chart.js.
